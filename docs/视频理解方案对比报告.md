# AI 文本模型理解视频：技术方案对比报告

> 调研目的：为 `D:\Project\Aurabot` 新建一个可复用的「视频理解基础模块」做选型依据。
> 查询日期：2026-11-24。价格/限制以本次抓到的官方页面为准；抓不到的一律标「未查到」，未做任何推算。
> 全文中 "Aurabot 现状" 部分来自对项目的只读浏览，未修改任何现有文件。

## 结论（推荐方案）

**推荐采用「混合 pipeline + 字幕/语音优先 + 抽帧/原生视频兜底」的路由式基础模块，不押注单一路线。**

核心判断：

1. **文本大模型不是真的"看视频"**，业内可行做法只有三类信息入口：①现成字幕/转写文本；②ASR 把音轨转成文字；③把视频抽样成图像（关键帧）或整段喂给原生视频多模态模型。四条路线各有覆盖盲区，单一路线无法同时覆盖"语音为主"和"画面为主"。
2. **性价比排序（一般情形）：现成字幕 > ASR ≈ 抽帧+VLM > 原生视频 API**。平台字幕是现成文本，几乎零推理成本；语音为主视频靠 ASR 最有效；画面信息只有抽帧/VLM 能拿到；原生视频 API 效果最完整但按 token 计费，长视频成本不可控，作为高价值兜底。
3. **Aurabot 已有可复用的半成品**：`src/bili/vision.js` 已实现"抽帧→VLM 描述"，`src/bili/api.js` 已能拿 B 站字幕，`src/chat/hub.js:1273` 有 `fetch_ptt_text`、`src/chat/hub.js:1294` 和 `src/modules/voice/index.js:62` 有 DSH `speechToText` 调用。新模块应把这些能力收拢成统一接口，而不是重写。
4. **接口形态建议**：按 Aurabot 模块规范做一个 `video-understand` 基础模块，`setup(api)` 同步返回导出 `understand()` / `supports()` / `estimate()` / `status()`，其他模块用 `api.use('video-understand')` 调用；配置项放 `config.ext.videoUnderstand.*`，缓存与中间产物放 `api.dataDir('video-understand', ...)`。

推荐路由优先级（默认策略）：
平台链接 → 尝试现成字幕 →（无字幕/音轨有语音）ASR →（画面信息不足/画面为主）抽帧+VLM →（复杂时序/动作理解且预算允许）原生视频多模态 API。

## 形态×路线适配矩阵

| 视频形态 | 首选 | 次选 | 理由（效果/成本/延迟） |
|---|---|---|---|
| 1. 聊天短视频/片段（几秒~几分钟） | 若有音轨语音：ASR；若有字幕：字幕提取 | 画面为主时抽帧+VLM；短且高价值时原生视频 API | 体量小、成本都低；语音片段 ASR 最快最准；画面片段抽 3–6 帧够用；原生 API 延迟高、性价比低 |
| 2. 平台长视频（B 站/YouTube，常有现成字幕） | 平台字幕提取（yt-dlp / BBDown / `api.subtitle()`） | 无字幕时 ASR；需要画面摘要时叠加抽帧；复杂时序用原生视频 API | 成本几乎为零且文本质量高；长视频整段喂原生 API 按 token 计费很贵；字幕+少量帧即可覆盖大多数问答 |
| 3. 语音为主（画面次要，如播客/讲解/语音条） | ASR（GLM-ASR / FunASR-Paraformer / QQ `fetch_ptt_text` / DSH `speechToText`） | 平台字幕（若在平台且有 CC）；原生视频 API 的音轨理解 | 信息几乎全在音轨，ASR 直达；抽帧对语音内容无意义；GLM-ASR 单价 16 元/M tokens（约 0.0002 元/秒）[来源](https://docs.bigmodel.cn/cn/guide/start/pricing) |
| 4. 画面为主（表情包/演示操作/风景，语音少或无） | 抽帧 + VLM | 原生视频多模态 API（动作/时序关键时） | 信息在画面，字幕/ASR 无效；抽帧成本可控且现成实现可复用；原生 API 对精细动作与时间定位更强但更贵 [来源](https://docs.bigmodel.cn/cn/guide/models/vlm/glm-4v-plus-0111) |

## 模块接口设计建议

贴合 `docs/MODULE-TUTORIAL.md`、`docs/PURPOSE_MODULE_API.md` 与 `src/modules/API.md`：新建内置模块 `src/modules/video-understand/`，含 `module.json`、`index.mjs`、`README.md`、`LICENSE`；`setup(api)` 同步返回导出，配置放 `config.ext.videoUnderstand.*`。

**对外接口（`api.use('video-understand')`）**

- `understand(input, options?)` → Promise<结果对象>，核心入口。`input` 可为：本地文件路径、公网 URL、B 站 BV 号/链接、YouTube 等平台链接（扩展名与 host 识别路由）。
- `supports(input)` → 返回该输入可行的路线列表及原因（供上层做 UI 提示/预估）。
- `estimate(input, options?)` → 预估路线、token/费用区间、耗时档位（无确切数字时返回档位而非伪精确值）。
- `status()` / `state()` → 运行状态、缓存命中率、最近错误，便于观测。

**输出结构（建议统一为结构化对象）**

```
{
  input: { kind: 'local'|'url'|'bilibili'|'youtube', raw },
  meta: { durationSec?, sizeBytes?, mime?, platform?, title?, sourceUrl? },   // 未取到的字段为 null
  transcript: { text, source: 'subtitle'|'asr'|'native'|null, language?, segments?: [{start,end,text}] },
  visual: { description, frames: [{ tSec, dataUrlOrPath, width?, height? }] },
  events: [{ tSec, label }],   // 原生视频 API 命中时填充事件时间点；否则 []
  route: { chosen, tried: [...], fallbackReason? },
  cost: { estimatedTokens?, actualTokens?, note? },   // 无法精确统计时仅给 note
  cachedAt?: string
}
```

**内部路由（默认顺序，均可配置覆盖）**

1. 识别输入：平台链接 → 调对应下载/字幕工具；本地文件/直链 → 探测音轨与时长（ffmpeg 可用时）。
2. 有现成字幕（B 站 `api.subtitle()`、yt-dlp `--write-subs`、BBDown 字幕）→ 直接产出 transcript，跳过 ASR。
3. 无字幕但有音轨 → ASR：优先 QQ `fetch_ptt_text`（聊天语音条）/ DSH `speechToText`；长音频或需要说话人分离时切到 GLM-ASR-2512 或本地 FunASR-Paraformer（走 `api.core.local.call(slot, args)` 本地脚本槽位，与现有 `video`/TTS/生图的 local 模式一致）。
4. 画面信息需求未满足（`needsVisual=true` 或识别为画面为主）→ 抽帧 + VLM：直接复用 `src/bili/vision.js` 的策略（最多 12 帧、默认 6、跳过首尾 5%、缩放宽 512、JPEG、魔数校验），通过 `api.ask` 调用当前模型。
5. 仅当上述不足以回答且预算允许 → 原生视频多模态 API（优先国内可用且价格透明的智谱 GLM-4V-Plus-0111 / GLM-4.6V 系；按 `api.config()` 中的 apiKey/model 调用）。每层失败都降级到下一层，并把原因写进 `route.tried`。

**配置项（`config.ext.videoUnderstand.*`）**

- `enable`: 模块开关；`maxDurationSec`/`maxSizeBytes`: 输入上限与超限拒绝策略。
- `route.preferSubtitle`: 默认 true；`route.asrEngine`: `qq` | `dsh` | `glm` | `funasr-local`；`route.vlmModel`: 走 `api.ask` 的模型名；`route.nativeProvider`: `zhipu` | `none`（默认 none 以控成本）；`route.needsVisualKeywords`: 触发抽帧的关键词/规则。
- `frame.count`（默认 6，范围 1–12）、`frame.width`（默认 512）、`frame.timeoutMs`（默认 15000）、`frame.maxBytes`（默认 2MB）。
- `download.ytDlpPath` / `download.bbdownPath`：工具路径或 PATH 依赖检查；`download.cookiesFrom` 指定登录态来源（敏感配置不落日志）。
- `cache.enabled`（默认 true）、`cache.ttlSec`、`cache.maxEntries`；`native.apiKey` 放安全配置，不写入模块文档示例明文。

**缓存与成本控制**

- 缓存 key = 路线无关的输入指纹（URL 归一化后 hash / 本地文件 mtime+size hash）+  options 中有影响的子集（如 `needsVisual`、`frame.count`）；命中直接返回结构化结果，缓存放 `api.dataDir('video-understand', 'cache')`，与 `docs/PURPOSE_MODULE_API.md` 的状态文件模式一致。
- 字幕优先：字幕命中后默认不再调 ASR/VLM，除非 `needsVisual=true`；抽样率与帧数按视频时长分档（短片段 3–6 帧，长视频每段 6–12 帧），避免长视频无节制抽帧。
- 原生视频 API 默认关闭或仅在 `budget.allowNative=true` 时启用；对同一输入先检查缓存，禁止重复付费调用；智谱 Batch API 5 折可用于非实时批量任务 [来源](https://docs.bigmodel.cn/cn/guide/start/pricing)。
- 失败不得吞掉：每个降级原因写进结果，便于上层决定是否需要人工介入。

## 风险与待确认项

1. **价格时效性与缺口**：本次仅智谱/百炼文本模型价格核实完整；Gemini、豆包、百炼视觉模型、火山 ASR 的价格与限制均**未查到**；价格为 2026-11-24 快照，实施前需复核。
2. **数据合规与隐私**：用户聊天视频/本地文件可能含隐私；上传第三方 API 前需确认用户授权与项目隐私策略；平台视频下载可能违反平台 ToS；BBDown 部分画质需登录态/cookies [来源](https://www.bber.cn/projects/bbdown/)。
3. **依赖可用性**：ffmpeg 是否随 Aurabot 部署（现有 `findFfmpeg` 依赖）；yt-dlp/BBDown 的二进制与 .NET 运行时、网络可达性；插件 capabilities 需声明 `network`/`filesystem`/`process`，若走 plugin-internals 触发子智能体委派红线需按 `docs/MODULE-TUTORIAL.md` 处理。
4. **路由误判**：ASR 与画面描述的触发条件需要真实样本调参；抽帧可能漏关键帧；建议上线后以"字幕命中率/降级次数/费用"三项指标迭代。
5. **现有代码复用边界**：`src/bili/vision.js` 与 `src/bili/api.js` 的 B 站相关实现可直接借鉴/提取为通用函数，但需确认不破坏 `src/bili/duty.js` 既有流程（只读调研未做改动）；`api.use('video-understand')` 需在 `setup(api)` 内取导出，不要提前缓存 [来源](src/modules/API.md)。
6. **OpenAI 视频能力未确认**：本次未查到官方视频输入 API，不要把任何第三方封装当作官方能力写入实现。
